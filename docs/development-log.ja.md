# 開発記録

[English](development-log.en.md) | [日本語](development-log.ja.md)

この記録は、M-Anchor Appの目的、判断理由、変更、確認結果を第三者が追えるようにするためのものである。既存の研究用評価記録とは別のアプリ開発記録として管理する。

## 2026-09-30：小さな配布版の方針

接続方式を専用Pythonクライアント一種類、保護対象を案件記録の更新一種類に絞った。モデルは提案のみを出し、外部のGateとストアが更新の可否を決める。画面から規則を迂回する承認機能は設けない。

試作版の名称はAnchor Control。基本動作の確認後、本計画をM-Anchor Appとし、専用リポジトリ `iseyan/M-Anchor-App` を作成した。当初の[計画メモ](../plans/m-anchor-app-plan-2026-09-30.ja.md)は日付付き記録として保持する。

## 2026-09-30：v0.1 / v0.2の観察

| 観察 | 得られた資料 | 読み取れること |
| --- | --- | --- |
| 固定の根拠なし確定案が拒否された | before/after、reject、invalid_transition、readback_verified=trueを含むJSON | この不正な提案はGateを通らず、正本を維持した |
| 固定の正当更新が保存された | commit、Version 1→2、h_B、再読込確認を含むJSON | 認可済み証拠に適合した更新は保存された |
| 実モデル経由のDEMO-HOLDが変更なしになった | モデルIDと利用量、no_commit/no_state_change、before/afterが同じJSON | モデルの案とGate処理を経て、未決が保持された |
| 実モデル経由でDEMO-UPDATEを操作した後にh_B・Version 2を表示 | 利用者が提示した案件一覧 | 操作後の状態が期待した正当更新の結果と一致した。今回提示された資料は一覧であり、完全な実行ログではない |

実モデルの提示ログには `gpt-5.4-mini-2026-03-17` が記録されていた。ここから一般的な攻撃成功率や、任意の入力に対する保証は算出しない。

操作中には、手動でキーを探す負担、サーバーが起動していないときの接続エラー、対象案件の選び違い、更新済み案件で「変更なし」になる理由の分かりにくさが見られた。v0.3ではこれらを改善対象とした。

## 2026-09-30：v0.3の変更と理由

| 変更 | 理由 |
| --- | --- |
| 起動確認後のブラウザ表示と自動接続 | キー転記と起動待ちの操作を減らす |
| 対象を未選択で開始、実行ボタンにも案件名を表示 | 意図しない案件での実行を減らす |
| 更新前後と「保存・拒否・変更なし」を表示 | 発言の成功と正本の変更を取り違えないため |
| 新しいデモを別フォルダに作成 | 実演を繰り返しても以前の正本と記録を残すため |
| JSONの確認記録と第三者向け資料 | 接続検討や説明時に、対象・条件・結果・限界を一緒に示すため |

Gateと形式核、モデル接続処理、専用クライアントは変更していない。操作の改善が検査規則の緩和にならない構成を採った。

開発中、記録出力処理でGate内部のトランザクションと外側のトランザクションが重なり、25件中1件が失敗した。Gateを変更せず、SQLiteのbackup機能による一貫したメモリ内コピーから記録を読む構成へ修正した。修正後は25件すべてが通過した。

UIの実コードを、最小限のDOM代替と実HTTPサーバーで動かす確認も追加した。これはブラウザの描画やブラウザ固有のセキュリティ動作を確認したものではない。詳しくは[検証記録](validation-v0.3.ja.md)を参照する。

実モデル経由の未決保持、実モデル経由の正当更新、固定の不正案の提出を順に案内した後、利用者から三件の履歴が提示された。番号1はDEMO-HOLDの「変更なし / no_state_change」、番号2はDEMO-UPDATEの「保存 / accepted」、番号3はDEMO-HOLDの「拒否 / invalid_transition」で、期待する結果と一致した。

## 2026-10-01：v0.4の実行記録

v0.3で受領したJSONでは、最後の固定デモに関する情報だけがページ内に残り、先の二件のモデル情報を確認できなかった。この欠落を次版の対象とした。

正本更新・判定・実行情報を同じトランザクションに保存する。別々に保存すると、正本だけ進んで説明記録がない状態が生じるためである。独立した再読込は更新後の観察として記録し、中断時には確認済みにしない。

提出経路は利用者やモデルの自己申告に頼らず、サーバーの処理経路で区別する。モデル情報は内部の一回限りのチケットで案件と提案の生バイトに結び付ける。従来のクライアントAPIでは、外部で生成された提案の作者までは断定しない。

旧版の履歴はそのまま保ち、新しい表を追加する。元から残っていない日時やモデルIDは未記録とする。同一提案を繰り返しても区別できるよう、画面とJSONで履歴番号を使用する。JSONは全件、画面の一覧は最新100件とし、詳細を選ぶと過去の原文・判定・状態を表示する。

34件の自動テストが通過した。再起動・旧スキーマの移行・SQLエラー時のロールバック・103件の全件出力を確認した。モデルの応答は模擬し、有料APIを使用していない。UIロジック確認も通過した。[検証記録](validation-v0.4.ja.md)に環境と限界を記載した。

同日、利用者からGitHub ActionsやAWSによる自律化について質問があった。開発の自動化とアプリ運用の自動化を分け、[構成計画](automation-plan.ja.md)に記した。この版ではCIの有効化やクラウドの作成・配備は行っていない。

## 2026-10-01：v0.5の検証・配布自動化

利用者のv0.5作業開始の指示を受け、GitHub Actionsでの検証と配布物作成を実装した。アプリの検査規則と実行記録はv0.4のものを使い、検証したソースから誰でも同じ手順で配布物を作れるようにする。

実行環境はLinuxの最低対応版Python 3.10と3.13、利用者の環境に合わせたWindows/Python 3.13とした。UIロジックにはNode.js 24を使用する。失敗した版のZIPは作らず、検証ログを保存する。APIキーを使うモデル試験は実行しない。

配布処理ではソースのチェックサム、ZIP内の全バイトを照合する。入力の変更を見逃さないこと、接続キーや実DBを梱包しないこと、Windowsの改行変換で不要な不一致を起こさないことを対象にした。[v0.5検証記録](validation-v0.5.ja.md)に結果を残す。

v0.5の初回Actions実行では、三つの検証環境と配布ジョブがすべて成功した。[実行 #1](https://github.com/iseyan/M-Anchor-App/actions/runs/36743819362)の元ソースは `6a986b396fd1cba895e959ddc9982db9054b379b`。各環境のログとZIPがArtifactsに作成され、APIから取得した結果を[検証記録](validation-v0.5.ja.md)に残した。アプリの判定用APIを外部へ公開したり、AWSへ配備したりする処理は追加していない。
