# M-Anchor App — 開発・配布計画メモ

2026年9月30日（日本時間）  
状態：ローカル試作版 v0.2 の基本動作を確認。小規模な配布版に向けて操作を整理する段階。

## 1. 名称と目的

本計画を **M-Anchor App（Mアンカーアプリ）** とする。現在の試作版の画面名は「Anchor Control」。今後の配布版では名称と説明を統一する。

目的は、AIが作った記録の更新案を検査し、定めた条件を満たす更新だけを正本に保存することである。根拠のない確定によって未決の候補が失われることを防ぎ、認可された証拠による更新は通す。

基本原則は **Model proposes; deterministic layer commits.** モデルは提案を作り、モデルとは別の規則に基づく検査・保存処理が更新の可否を決める。

## 2. 最初の配布版の範囲

接続方式は専用Pythonクライアント一種類、操作は案件記録の更新一種類に絞る。現在のモデル接続はOpenAI Responses API一種類で、利用者がAPIキーとモデルIDを指定する。

Windows上でローカルサーバーを起動し、ブラウザから操作する。正本はローカルのSQLiteに保存する。現在の試作版はPythonの導入が必要で、追加のpipインストールは不要である。

保護対象は、このストア内の案件記録である。証拠の採用可否と解釈はモデルの外で設定する。外部ツールの実行制御、証拠内容の真偽判定、一般的な会話全体の評価は初版の対象に含めない。

## 3. 実装の構成

| 部分 | 役割 |
| --- | --- |
| ブラウザ画面 | 接続、案件選択、提案生成の依頼、判定と履歴の表示 |
| モデル接続処理 | 案件の状態と認可済み証拠・解釈を渡し、更新案を生成させる |
| 専用Pythonクライアント | 状態を取得し、モデルが返した更新案をAPIへ提出する |
| Gateとストア | 更新案を検査し、許可した変更と監査記録を保存する |

クライアント向けの主要APIは次の二つとする。

- `GET /v1/cases/{id}`：現在の状態と、その案件に認可された証拠・解釈を取得する。
- `POST /v1/cases/{id}/proposals`：更新案を提出する。

モデルに管理キー、DBへの直接アクセス、シェルや外部ツールを渡さない。モデルの返した提案文は、JSONの修復や項目の差し替えをせずに提出する。

## 4. 維持する更新規則

- 案件ID、参照version、参照hash、提案の形式を検査する。
- モデルが「認可済み」と書いても、証拠認可や更新権限を変更しない。
- 認可された証拠と外部の解釈が支持しない候補削除を認めない。適用できる証拠がなければ候補を保持する。
- 拒否または変更なしの場合、正本の状態・version・hashを進めない。
- 許可された変更は保存し、別のDB接続で正本を再読込して結果を確認する。

初期版の証拠認可と解釈は初期化時の設定に限定する。画面の承認操作でこれらの規則を迂回する経路は設けない。

この境界はアプリを通る更新に適用する。同じOS利用者の権限でDBを直接書き換えられるプログラムを隔離する機能は、現在の試作版にはない。

## 5. 現時点の確認結果

ローカルアプリの接続・保存動作について、次の結果を確認した。

| 操作 | 結果 | 確認資料 |
| --- | --- | --- |
| 固定の根拠なし確定案を提出 | `DEMO-HOLD` を拒否。両候補・version・hashを保持 | 判定JSONと再読込確認 |
| 固定の認可済み証拠による更新案を提出 | `DEMO-UPDATE` を `h_B` に更新。Version 1から2へ進行 | 判定JSONと再読込確認 |
| 実モデル経由で証拠のない案件を処理 | `DEMO-HOLD` は両候補・未決・Version 1を維持。`no_commit / no_state_change` | モデル利用情報と判定JSON |
| 実モデル経由で認可済み証拠による更新を操作 | `DEMO-UPDATE` が `h_B`・resolved・Version 2になった | 利用者の操作後の案件一覧 |

実モデル経由の提示ログに記録されたモデルは `gpt-5.4-mini-2026-03-17`。また、開発環境ではHTTP経路と模擬モデル応答を含む18件の自動テストが通過している。

この確認は、人工的な二案件を使ったアプリの基本動作確認である。実モデルが変更不要の案を返した結果と、不正な案をGateが拒否した結果は区別して記録する。既存の研究用評価記録とは別の開発記録として扱う。

## 6. 次の実装・配布作業

まず操作を簡潔にし、コードを編集せずに起動から結果確認まで進める配布版を作る。

1. **起動と接続**：起動完了を確認して画面を開く。管理キーの設定手順を減らし、接続状態を明示する。
2. **案件選択**：未決保持用と正当更新用の違いを画面で説明する。実行直前に対象案件が分かる表示にする。
3. **結果表示**：「保存」「拒否」「変更なし」を区別し、理由と更新前後を短く示す。通信失敗で結果が分からない場合は「結果未確定」と表示する。
4. **デモの再実行**：更新済み案件と未実行案件を区別する。新しい試験用データを、既存データを上書きせずに作れるようにする。
5. **配布物の整備**：名称、起動手順、対応環境、API利用条件、ライセンスを整理する。利用者のキーやDBを含めずに配布する。実行ファイル化は、この操作整理の後に検討する。

接続先の追加、複数エージェント対応、稼働中の証拠追加・撤回、外部ツールへの書込みは、その後の拡張課題とする。

## 7. 最初の配布版の到達目標

利用者がPythonコードを編集せず、起動・接続・案件選択・実行・結果確認を行えること。根拠のない確定案は正本を変えず、認可された証拠による更新は保存され、再起動後にも保存状態を確認できることを到達目標とする。

画面には操作と結果を簡潔に示し、提案内容、使用した証拠、更新前後、version・hashは必要に応じて開ける詳細に置く。機能を追加する際も、正本への更新経路と証拠認可の境界を維持する。
